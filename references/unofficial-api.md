# 非公式APIが壊れたとき

## 求める材料

| 材料 | 種類 | 必須 | 形 | 無いとき |
|---|---|---|---|---|
| 起きたこと（例外の型・`code`・`msg`、HTTPステータス、復号の失敗） | 対象の記録 | ○ | エラーの文 | 判断できない |
| 使っているアプリとアカウントの種類（RENPHO Health か、旧Renpho か） | 導入先の環境 | — | アプリ名 | RENPHO Health として答える |

## 答え

1. **RENPHOに公式APIは無い。** 叩いているのはRENPHO Healthアプリの内部APIで、仕様は公開されておらず、予告なく壊れる。
2. **旧ホスト（`renpho.qnclouds.com`）には戻さない。** 旧Renphoアプリ専用で、RENPHO Healthのアカウントでは動かない。
3. **壊れたら、同じプロトコルを追っている次の実装との差分を見る。** どれも採用はしていない。仕様の参照先として使う。Issue に、先に踏んだ人の報告と回避策が出ていることが多い。
   - `danvaneijck/renpho-api`（PyPI `renpho-api`）：最も追従が早い
   - `forkerer/RenphoGarminSync-CLI`：元のリバースエンジニアリング
   - `StartupBros-com/renpho-mcp-server`
4. **差分を取り込んだら、`renpho_api.py` の定数とこの判断を直す。** 呼び出し側には手を入れずに済むようにする。
5. **ログインの拒否と、プロトコルの破損を分ける。** `RenphoAuthError` で「ログインに失敗」と出たら、まず認証情報を疑う（[認証情報の扱い](credentials.md)）。正しい認証情報で、復号の失敗・`code=-114`（本文を復号できない）・`code=104`（ユーザー名かパスワードの誤り）・想定外の `code` が続くなら、プロトコルの破損を疑う。`code=104` は、アプリの版が古いときにも返る。
6. **ログインが拒否されたら、ログインを繰り返さない。** `renpho_auth.py check` を1回だけ流して `code` と説明文を確かめ、答え3の差分を見てから試す。

## 道具

- `uv run <skill-dir>/scripts/renpho_auth.py check`：`debug=True` で、エンドポイントごとの `code` と説明文を出す。
- `uv run <skill-dir>/scripts/probe_fields.py --json <保存先>`：応答の形が変わっていないかを、全件で確かめる。
- 道具の中に実装してあること：ログインを含むすべての要求に `appVersion`・`platform` のヘッダーを付ける。説明文は `msg` が無ければ `message` から読む。成功は `code` の 0・200・101 か、説明文の `success` で見分ける。

## 理由

1. （知見）RENPHOは公式APIを公開していない。出典なし。旧ホストから現行ホストへ移ったとき（理由2の表）と、2026-10 のログインの変更（理由5）で、少なくとも2回壊れている。
2. （原因・知見）次の表のとおり。

   | 世代 | ホスト | 状態 |
   |---|---|---|
   | 旧 | `renpho.qnclouds.com`（sign_in → list_scale_user → measurements/list） | 旧Renphoアプリ専用。RENPHO Healthのアカウントでは動かない。参照実装（hass_renpho など）も更新停止。レート制限やIPの遮断の報告がある |
   | 現行 | `cloud.renpho.com` | RENPHO Health（青いアイコン）のアカウント用。このスキルが使う |

3. （原因）2026-10-23、答え5の破損の回避策は、`danvaneijck/renpho-api` の Issue #12・#10 にあった。本体のコードはまだ直っていなかった。
4. 記録なし。
5. （原因）2026-10-23、保存済みのtokenが403になったので再ログインしたところ、正しい認証情報で `code=-114` が返った。`msg` は空で、説明文は `message` にあった。`danvaneijck/renpho-api` の Issue #12（2026-10-19）・#10（2026-09-10）にも同じ報告があった。ログインの要求に `appVersion`・`platform` のヘッダーを付け、アプリの版を 6.6.0 から 7.0.0 に上げると、`code=101` で通った。2つを同時に直したので、片方だけで通るかは、こちらでは確かめていない。Issue では、ヘッダーだけ直して版が 6.6.0 のままだと `code=104` が返ると報告されている。
6. （根拠）壊れているうちにログインを繰り返しても、通らない。成功すれば、そのたびにスマホアプリがログアウトされる（[セッションとトークン](session.md)）。

## 却下した案

| 案 | 理由 |
|---|---|
| 参照実装（`renpho-api` など）をそのまま依存に入れる | 採用しなかった理由の記録は無い。仕様の参照先としてだけ使っている |
| Issue の回避策のとおり、`cellphoneType` を `MCP-Server`、`bindingList` を `["2"]` に変える | 2026-10-23、変えずにヘッダーと版だけで通った。`bindingList` を変えると、返る機器の紐付けが変わるおそれがある |

## 当てはまる範囲と限界

- RENPHOが公式APIを出したら、このスキルの道具ごと見直す。
- アプリの版 7.0.0 が、いつまで受け付けられるかは分からない。また `code=104` か `-114` が出たら、答え3の差分を見て版を上げる。
